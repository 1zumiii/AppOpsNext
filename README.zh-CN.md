# AppOpsNext

[English](README.md) | **简体中文**

AppOpsNext 能提供更精细的应用权限控制、记录和监测，保护用户的隐私，它借助 [Shizuku](https://shizuku.rikka.app/) 运行，无需 root，主要回答用户关心的四个问题：

* **配置：** 我允许了什么？
* **事件：** 谁在访问什么？
* **结果：** 系统最终是允许还是拒绝？
* **观察者：** 还有谁在监听这些变化？

---

- **更精细的权限控制：** 每个应用的相机、定位、剪贴板等权限都能单独控制。改完自动回读，校验是否生效。
- **模板与新装应用：** 常用的限制可以存成模板，一次套到多个应用上，新装的应用也能自动套用。
- **谁用过、什么时候用的，一目了然：** 权限历史有每日图表、时间线和按应用统计，能按时间范围和应用筛选，被拒绝的次数也一并统计。系统只留 7 天的明细，开启历史记录持久化后，AppOpsNext 会替你接着存下去。
- **访问监测（实验性）：** 定向监测指定应用的指定权限，实时通报每次访问及系统最终是允许还是拒绝，并记录下来供后续查询。系统本身不会逐条记录被拒绝的访问。
- **权限变更监听者（实验性）：** 查看当前有哪些进程在监听权限设置的变化。
- **拒绝特权越界：** 特权操作只限于固定的 AppOps 命令和接口，不执行任意 shell 命令。所有记录本地存储，除了检查更新不联网。

## 主要功能

| 功能 | 说明 |
| --- | --- |
| 应用列表 | 浏览当前用户的应用，按名称或包名搜索，可选择是否显示系统应用。 |
| AppOps 管理 | 查看应用按包和按 UID 两种范围的模式，改完自动校验。 |
| 模板与批量操作 | 创建可复用的规则并调整顺序，把模板套到多个应用上，或一次改好一个应用的多项权限。 |
| 新装应用 | 可选择自动套用模板，补处理还没完成的安装，查看每条规则的执行结果。 |
| 权限历史 | 查看权限使用分布、应用统计和时间线，能按时间范围和应用筛选，自选要看的权限并排序。还能把单条记录保存到 7 天以后。 |
| 设置与诊断 | 支持简体中文、英文或跟随系统，查看连接状态和诊断报告，有新版本时不会有打扰性弹窗提示，不强制更新。 |
| 实验性功能 | 定向监测App和权限，被使用时推送通知。一个监测点由“应用 + 权限”组成，每个监测点都能单独设置通报间隔、提醒方式、通报内容，以及是否只在应用不在屏幕上时通报。监测对象需自行选定，开启时会先检查设备的兼容性。每条监测记录都可供查询。 |

## 安装与上手

### 运行要求

- **Android 15 及以上**（API 35+）。
- **Shizuku 13 及以上**，已启动并授权给 AppOpsNext。
- 内置的原生后端只支持 **ARM64**，其他 CPU 架构还未验证。

用 ADB 或无线调试启动 Shizuku 时无需 root，但 AppOpsNext 的特权操作始终依赖Shizuku。

1. 安装并启动 [Shizuku](https://shizuku.rikka.app/)。
2. 在[最新 Release](https://github.com/1zumiii/AppOpsNext/releases/latest) 下载 APK 并安装。
3. 打开 AppOpsNext，Shizuku 弹出授权请求时点允许。
4. 选好应用和权限，看过确认信息后再修改。

可复用的规则在**模板**页配置，系统记录在**历史**页查看。
新装应用自动套用模板默认关闭，建议先配好规则再打开。

更新时直接覆盖安装新版 APK，设置均会保留。
设备重启后如果 Shizuku 没有运行，或者授权被撤销，要先恢复连接才能读取或修改系统状态，
已保存的历史记录不受影响，依然可以查看。

## 历史记录从哪里来

历史数据来自 Android 系统的权限记录日志。有单条访问记录的权限，AppOpsNext 优先显示单条记录。
剪贴板这类没有单条记录的权限，就显示系统按时间段累计的次数。
记录能保留多久、时间精确到什么程度，均由设备决定，所以这不是一份完整的审计日志。

- 每项权限最近一次读取成功的记录会留存本地，重新打开应用时直接显示，并标明更新时间。
- 五分钟内回到页面会直接用现有记录。更早的记录或还没读过的权限，要同时满足历史页正在显示、应用在前台、后端已连接这三个条件才会读取，定时刷新也一样。
- 手动刷新无论新旧都会重新读取，每项权限读完立即更新。读取失败时保留上一次的结果，同时给出错误提示。
- 第一次读取成功之前，页面会区分“还没读取”和“确实没有记录”。

这部分本地记录只是最近一次读取的缓存，存在应用的私有目录下，不参与 Android 备份，清除应用数据或卸载应用后就没了。

### 历史记录持久化

单条访问记录系统只保留 7 天，再往前就只剩按时间段累计的次数，看不出具体时间。在设置内打开“历史记录持久化”开关后，AppOpsNext 会把所选权限的单条记录另存本地。能勾选的只有相机、麦克风、精确位置和大致位置，因为系统只提供这几项留单条记录。

- 第一次会按历史页已选的权限来勾选，之后两边互不影响。
- 历史页上的权限，刷新时顺便保存。其他勾选了的权限在打开应用时补存，最多 6 小时一次。所以理论上只要一周内打开过一次应用，就不会断档。
- 没存到的时段，用 30 天内的时间段统计来补。某个时间段如果和已存的记录有重叠，只算记录没覆盖到的那部分访问。系统有时会把几次访问并成一条记录，所以这个数目可能比实际略多。
- 最多保存 10 万条，存满后先删最早的。记录只保存在本地，不参与备份，自行管理或删除。
- 如果存档文件读不出来（比如装回了旧版本），AppOpsNext 不会覆盖它，而是暂停保存。

被拒绝的访问，系统不会留下单条记录。想逐条查看，请用实验性功能里的访问监测，记录可在“监测记录”里查询。

## 修改 AppOps 之前的须知

**AppOps 和 Android 运行时权限是不同的。** 应用如果没被授予某个运行时权限（例如**相机权限**），把对应的 AppOp 设成“允许”也不会让它获取该权限。Android 或厂商的策略还可能改写甚至拒绝你设置的模式。遇到运行时权限导致的失败，AppOpsNext 会说明原因，并给出跳转到该应用系统设置的入口。

每次修改可按以下的流程进行核对：

```text
读取并确认原来的状态
  → 写入新的模式
  → 回读校验
  → 失败时尝试恢复原来的状态，并核对是否改回
```

手动修改、批量操作和自动套用模板共用同一个队列，一次只执行一项。
命令执行完不代表修改成功，核对和恢复的结果会分别报告。
失败后的恢复只是尽力补救，不保证一定成功。

按 UID 修改可能同时影响共用这个 UID 的多个应用，确认界面会把它们都列出来。
自动切换修改范围也有限制，避免在你不知情的情况下扩大影响。
批量操作会逐个报告每个应用的结果。

## 使用到的权限和网络

| 权限 | 用途 |
| --- | --- |
| `QUERY_ALL_PACKAGES` | 管理 AppOps 需要查询设备上所有的应用。 |
| `INTERNET` | 只用来检查有没有新版本。 |
| `POST_NOTIFICATIONS` | 通知新装应用自动套用模板的结果，以及实验性访问监测的实时推送。 |
| `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE` | 访问监测开启期间保持在后台运行，确保能收到系统的回调。 |

检查更新只访问一个 GitHub 公开接口，不发任何其他请求。它不会强制更新，不会自动下载或安装任何东西，也不会弹窗或发通知。有新版本时，只会在设置页的“应用版本”旁边显示。**不会上传任何用户数据。**

诊断报告不会自动发到任何地方。它只在设备上生成，你主动点复制才会进剪贴板。

## 常见问题

- **连接不上：** 确认 Shizuku 正在运行并且已授权 AppOpsNext，再到**设置 → 连接与诊断**看详情。应用会首选内置的原生后端，启动失败会自动尝试改用 Shizuku UserService。
- **某个模式设了不生效：** 查看对应的 Android 运行时权限和回读核对的结果。有些系统限制是 AppOps 管不到的。
- **历史记录太旧或不全：** 查看更新时间，尝试手动刷新，并确认后端已连接。能读到哪些记录可能因ROM而异。
- **访问监测一直没有提示：** 这是实验性功能，依赖的特权接口并不保证每个 ROM 都有。关掉再重新打开，查看自检结果，它会区分“设备不支持”还是“部分监听没注册上”。另外确认至少选了一个监测点，默认监测点为空。
- **监测计数和应用实际调用次数对不上：** 计数是被通报的次数。Android 可能一次调用报好几个事件。如果监测点设了通报间隔，间隔内的访问就不会通报。只统计当前用户空间里选中的应用，监测结果也不是精确的 API 调用记录。
- **高频权限把通知刷满了：** 高频权限例如某地图应用的定位，每送一次定位结果就上报一次，不设间隔的话每秒都会来一条。可以在“设置 → 实验性功能 → 监测设置 → 监测点设置”里给这个监测点设一个通报间隔。
- **开了“仅在应用不在屏幕上时通报”，还是会通报看得见的访问：** 判断依据是 AppOps 记录的进程状态，只有应用正显示在屏幕上才算作前台，前台服务不算。如果完全读不到这个状态，访问会照常通报。
- **强行应用后停止后监测不工作了：** 强行停止会移除监测服务，系统也不会再自动重启它。只要开关处于开启状态，重新打开 AppOpsNext 就能恢复。
- **熄屏一段时间后监测停了：** 部分厂商的电池优化或后台管理会直接结束应用进程，前台服务也无能为力，应用这边没无法控制。要长时间监测，请在系统设置里把 AppOpsNext 排除出电池优化，并在最近任务里锁定它。重新打开应用会自动恢复监测。
- **反馈问题：** 请附上设备型号、Android / ROM 版本、复现步骤，以及设置页里的诊断报告。公开提交 Issue 之前，建议自行检查日志并删除你不愿意分享的敏感信息。

## 从源码构建

需要 **JDK 17**、**Go 1.24+**，以及装好 **Platform 36 的 Android SDK**。
仓库自带 Gradle Wrapper。把 `JAVA_HOME` 指向 JDK 17，SDK 路径用 `local.properties` 里的`sdk.dir` 或环境变量 `ANDROID_HOME` 指定。

```shell
# 可选：Go 不在 PATH 里时，指定它的绝对路径。
# export GO_EXECUTABLE="/absolute/path/to/go"

./gradlew :app:assembleDebug
```

构建产物位于 `app/build/outputs/apk/debug/app-debug.apk`。Gradle 会顺便为 Android ARM64 交叉编译内置的守护进程，不需要额外用 NDK 构建。Debug 版在应用处于前台时会保持屏幕常亮，签名也和公开发布的 Release 版不同。

执行一次和 [Android CI](.github/workflows/ci.yml) 相同的检查：

```shell
(cd daemon && "${GO_EXECUTABLE:-go}" test ./...)
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug --no-daemon
```

### 签名的 Release 构建

公开发布版的签名文件不在 Git 仓库里。Release 构建需要
`.signing/appopsnext-release.keystore`，密钥别名为 `appopsnext`，并在环境变量里设置 `APPOPSNEXT_STORE_PASSWORD` 和 `APPOPSNEXT_KEY_PASSWORD`：

```shell
./gradlew :app:assembleRelease
```

构建产物位于 `app/build/outputs/apk/release/app-release.apk`。分发时请用自己的密钥库。要覆盖安装已有的版本，签名必须一致。维护者的验证和发布流程见[发布检查清单](docs/RELEASE.md)。

## 代码与文档

Android 代码位于 `app/src/main/java/dev/izumi/appopsnext/`。

| 路径 | 职责 |
| --- | --- |
| `presentation/` | Compose 界面、ViewModel 和界面状态。 |
| `appops/` | 命令、解析、修改范围的处理，以及带校验的写入流程。 |
| `nativebackend/`、`shizuku/` | 特权连接、原生管道和 UserService 备用方案。 |
| `apps/`、`settings/` | 应用发现、元数据缓存和用户设置。 |
| `templates/`、`newapps/`、`batch/` | 模板存储、新装应用检测、可中断续跑的规则执行，以及批量操作。 |
| `history/` | 系统历史的解析、刷新调度、本地缓存和单条记录存档。 |
| `diagnostics/` | 环境和连接报告。 |
| `monitor/` | 实验性功能访问监测：通过转发的 binder 调用注册监听、各监测点的通报设置、事件过滤、通知和监测记录。 |
| `update/` | 通过 GitHub API 检查新版本并比较版本号。 |
| 仓库根目录的 [`daemon/`](daemon/) | 用 Go 写的守护进程，只接受白名单里的命令。 |

## 项目背景

AppOpsNext 借鉴了旧版 App Ops（`rikka.appops`）的产品思路和使用流程，
但代码是从零独立实现的（clean-room）。它不是旧版的 fork、移植、修改版，也不是官方续作。

项目里没有旧版应用的源码、反编译代码、资源、品牌素材或配置数据，不依赖旧版应用，也不提供从旧版迁移配置的功能。AppOpsNext 和 RikkaApps 以及旧版 App Ops 的作者之间没有开发、背书或支持关系，使用 Shizuku 也不代表和它的维护者有从属关系。名称里的“AppOps”指的是 Android 内置的同名系统服务。
